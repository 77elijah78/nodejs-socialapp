# Explore, comment likes, engagement and bookmarks — implementation report

## 1. Scope and audit

Implemented on branch `arena/1275dc5e-nodejs-socialapp`, based on `main` at `cbee2b2044e20d40d7b850fef0c55629e5af4ea0`. No live database was changed, no deployment performed, and no merge performed for this task.

The existing application is Express/TypeScript + Prisma/PostgreSQL, with Kafka producers/consumers, authenticated post routes, soft deletion, a `saved_posts` composite primary key, per-post likes, threaded comments and a leased transactional `ReceiptOutbox`. Post/comment activity notifications already used that outbox. There was no Explore implementation, comment-like table, private-account flag, block model, approved-follow workflow, structured topics/hashtags model, or view-based engagement-rate metric.

Preserved the existing framework, service/controller/router boundaries, response envelopes, notification lifecycle, messaging/receipt/push behavior, and existing bookmark routes. Added recommendation signals to the existing durable outbox rather than publishing inside transactions or making counts Kafka-dependent.

### Main changes

* Explore ranking from popularity, real likes/live-comment counts, recency, bounded follower-normalized engagement, author/hashtag affinity, and author/topic diversity.
* Stable 15-minute ranked snapshots, account-bound cursors, seven-day served-post suppression, explicit refresh and exhaustion.
* Atomic, idempotent comment like/unlike with a database uniqueness constraint.
* Consistent engagement fields across post/comment create/read/list/update paths; legacy fields retained.
* Idempotent bookmarking and normal post objects in saved results; cursor pagination for saved posts and comments.
* Central post visibility checks for soft deletion, unavailable authors and private accounts, including protected local post media.
* One Kafka social-interaction topic, durable publication and idempotent canonical-state recommendation projection.

| `post_interests` | Small canonical-state interaction projection per account/post; no duplicate message/content store. |

New indexes:

* Comment-like uniqueness starts with `comment_id`, supporting counts and existence lookups; `(user_id,created_at)` supports user history.
* Saved-post `(user_id,created_at DESC,post_id DESC)` for stable cursor traversal.
* Likes `(user_id,created_at DESC,post_id)` and comments `(author_id,created_at DESC,id)` for bounded interest history.
* Live-post partial `(created_at DESC,id DESC)` and `(author_id,created_at DESC,id DESC)` indexes.
* Author `(account_status,is_private)` index for Explore/private visibility filters.
* Partial live-comment parent index for direct reply counts.
* Session account/expiry and expiry indexes; seen account/time and time indexes; interest account/update-time index.

Existing likes-by-post, comments-by-post/cursor, follow and bookmark primary-key indexes are reused. SQL-only partial indexes intentionally live in the migration; Prisma's schema does not describe their predicates.

After separate approval and backup, build the application/client with the new schema, run migrations against the explicitly approved target database, then roll out the backend:

```sh
npm ci
npx prisma generate
npm run build
npx prisma migrate deploy
```

Do not use reset, development migrations or db push against production. Normal `CREATE INDEX` in this additive migration can block writes during index construction: review table sizes and use an approved maintenance/online migration strategy on large installations before deploying. No production `EXPLAIN ANALYZE`, backfill, cleanup, deployment or live migration was executed here.

No new runtime secrets or environment variables are required. Existing Kafka startup creates/subscribes to configured topics; the deployment role must be allowed to create `social.interactions`, or an operator must pre-provision it with the existing partition/replication/retention policy.

## 3. API contracts

All paths below are relative to `/api/v1`. Existing success/error envelopes and JWT middleware are retained. Mutations derive the user from the login JWT; client-supplied counts, user IDs or flags are not used as engagement truth.

### Explore

`GET /posts/explore?limit=20`

* Requires authentication.
* `limit`: integer 1–50, default 20.
* `cursor`: opaque string returned in `meta.nextCursor`.
* `refresh=true`: create a new snapshot; must not be combined with a cursor.
* A request without a cursor creates a fresh snapshot, excluding recently served posts.
* New ranking excludes the viewer, followed authors, unavailable/private authors, deleted posts, posts older than 30 days and posts served during the preceding seven days.

```json
{
  "success": true,
  "message": "Explore",
  "data": ["normal enriched post objects"],
  "meta": {
    "limit": 20,
    "hasNext": true,
    "nextCursor": "<opaque cursor>",
    "expiresAt": "<ISO timestamp>",
    "exhausted": false,
    "algorithmVersion": 1
  }
}
```

The string in `data` is explanatory, not an actual response value. Actual responses contain post objects. No fabricated total recommendation count is returned.

Cursors identify a server-side session and position; ownership/expiry is checked in PostgreSQL, not trusted from the encoded cursor. Invalid/expired/evicted/other-account cursors and cursor+refresh requests return 400. A new refresh may evict the oldest session once five sessions are retained. Keep the new cursor when refreshing.

Pages recheck live authorization, author follow state and other-session served state; unavailable IDs are consumed without exposing content. Order is fixed within a session, but deleted/private/newly followed posts can disappear and counts/content remain live. Repeating a cursor can safely replay that session's page; do not automatically request an earlier cursor as a refresh. An extra empty final page can occur if remaining snapshot entries become unavailable. Empty/exhausted results are legitimate: the server does not reset seen history or silently reinsert old posts.

A served record means returned by the API, **not proof of a client impression**. Client display acknowledgement is not part of this implementation.

### Comment likes

| Method/path | Result |
|---|---|
| `POST /posts/:id/comments/:commentId/like` | Like, HTTP 200; repeated requests are idempotent. |
| `DELETE /posts/:id/comments/:commentId/like` | Unlike, HTTP 200; repeated requests are idempotent. |
| `GET /posts/:id/comments/:commentId/likes` | Normal comment with current like/reply counts and current-user flag; not a liker-list endpoint. |

All require JWT and UUID path parameters. Mutations return:

```json
{
  "success": true,
  "message": "Success",
  "data": {
    "commentId": "<comment UUID>",
    "likesCount": 3,
    "repliesCount": 1,
    "isLikedByCurrentUser": true
  }
}
```

The numbers above illustrate the shape; real responses use database counts. Deleted comments, mismatched post/comment IDs, unavailable/deleted posts and unauthorized private content return 404. Normal comment deletion remains author/post-owner authorized. No comment-like activity-notification type was invented; comment likes produce recommendation events only.

Existing `GET /posts/:id/comments?page=1&limit=20` now also accepts `cursor=<nextCursor>`. Ordering is `(createdAt ASC,id ASC)`. Existing page/limit behavior remains; cursor traversal starts strictly after the timestamp/ID tuple and ignores page offset. `meta.nextCursor` is provided when another row was found. Comment creation/retry/detail/list results include the engagement fields below. Replies remain the existing flat comment list with `repliedToId`; `repliesCount` counts immediate, non-deleted children, not recursive descendants. Deleting a parent does not invent a cascading soft-delete policy for its surviving replies.

`PATCH /users/me` also accepts an optional `isPrivate` boolean within the existing profile update schema. `GET /users/:username` returns this flag. Private mode is deliberately owner-only with the existing social graph; do not infer approved-follower access from a `Follow` row.

### Post engagement

`GET /posts/:id/engagement` — authenticated UUID path; returns:

```text
{success:true,message:"Success",data:{postId,likesCount,commentsCount,isLikedByCurrentUser,isBookmarkedByCurrentUser}}
```

Normal post objects on create/update/detail/feed/profile/liked/saved/Explore now include:

```text
likesCount: number
commentsCount: number
isLikedByCurrentUser: boolean
isBookmarkedByCurrentUser: boolean
```

Legacy `_count.likes`, `_count.comments`, `isLiked`, `isSaved`, media, author and ID fields remain. Comment counts exclude soft-deleted comments. Likes count canonical like rows. Anonymous public reads have both current-user flags false; authenticated reads resolve both flags in batches. Direct post details retain the first 20 comments, now with comment engagement fields and deterministic ordering.

Normal comment objects now include:

```text
likesCount: number
isLikedByCurrentUser: boolean
repliesCount: number
```

Post like/unlike responses retain their `message` and add enriched post fields. Share responses retain navigation metadata and now read the committed share count rather than returning a stale pre-transaction count plus one. Read results use normal database read semantics, not an immutable snapshot of concurrent interaction changes across subsequent HTTP requests.

### Bookmarks — reuse existing endpoints

* `POST /posts/:id/save`: existing HTTP 201, now idempotent rather than returning conflict on duplicate save. Unique account/post PK remains the final guard.
* `DELETE /posts/:id/save`: idempotent for available posts, HTTP 200.
* `GET /posts/saved?page=1&limit=20&cursor=<nextCursor>`: normal enriched post objects, not bookmark wrapper IDs or a comment-focused response.

Saved ordering is `(bookmark.createdAt DESC,bookmark.postId DESC)`; cursor encodes this tuple. Existing offset page clients continue to work. Entries retain the **original `post.id`** for normal post navigation, complete existing media metadata and author fields, canonical counts, and accurate current-user like/bookmark flags. Unavailable posts disappear from both results and total. Like the existing API, save/unsave of unavailable posts returns 404; internal saved rows can remain until physical deletion or availability returns.

Comment/saved cursor strings are validated timestamp/UUID tuples, not authorization credentials. Every query remains account/resource scoped. Explore is snapshot-ranked; do not interchange its cursor with comment/bookmark cursors.

### Limits

Explore: 30 authenticated requests/minute/IP. Engagement/comment-like routes and existing like/save mutations: shared 120/minute/IP limiter. These use the repository's in-process Express limiter pattern, in addition to application-wide controls. Shared multi-instance rate limiting remains an operational enhancement. Legacy pagination limits are retained outside Explore.

## 4. Ranking, cache and duplicate avoidance

Candidate generation is bounded to at most 500 unique posts, from:

1. Up to 300 most recent eligible posts.
2. Up to 100 eligible popular posts from an ID-only, global-public top-500 pool cached in-process for 60 seconds.
3. Up to 100 discovery posts: the freshest eligible post per author, using a PostgreSQL `DISTINCT ON` query and the author/live/cursor index. This gives smaller accounts a candidate slot when a prolific account floods the first two pools.

The cache stores only IDs, never content, counts, authorization or user-specific data. Concurrent cold requests share one pending calculation per process. Subsequent candidate/page queries always re-authorize. The popularity pool can lag by up to 60 seconds; restart simply recomputes it. Rank snapshots cache the expensive personalized ordering for 15 minutes in PostgreSQL and work across backend processes/restarts.

With `L=likes`, `C=live comments`, `F=author followers`, `H=age in hours`, `A=affinity`:

```text
engagement = L + 2*C
score = (1 + ln(1+L) + 1.5*ln(1+C)
         + 2*min(1, engagement/max(10,F)) + min(6,A)) / (1+max(0,H)/24)^0.8
```

Follower-normalized engagement is an explicit **proxy**, not a measured impression/view-based engagement rate. No fake view counts or user interests are created.

Affinity uses author and Unicode-hashtag overlap with up to 80 asynchronously projected interests, plus bounded canonical fallback history (40 likes, 40 bookmarks, 40 comments, 40 liked comments) when Kafka is delayed or historical projections do not yet exist. Interaction weights are like=3, bookmark=5, each live comment=2 capped at five per post, plus comment-like contributions capped at three. Author/tag affinity uses log weights and a score cap to limit domination/spam. Hashtags are parsed from content; there is no structured topic classifier or new ML infrastructure.

A greedy diversity pass penalizes repeated authors/topics and admits no more than two posts from one author in each 10-position window. If alternatives run out, it may end the snapshot early rather than fill the feed with one prolific account. An exhausted bounded pool is not proof there is no eligible content anywhere in the database.

Per-account row locking serializes refresh/seen writes across backend instances. `explore_seen` unique account/post keys and originating session IDs prevent overlapping sessions from delivering each other's newly served posts, while permitting cursor retries within the same session. Only posts actually returned are recorded; merely being ranked does not mark a post seen.

## 5. Kafka and transactional correctness

Added exactly one topic: **`social.interactions`**, using existing Kafka connection/admin/subscription/configuration and the existing leased outbox worker. No per-action topics, new consumer process or parallel outbox were introduced.

Events:

```text
post.created
post.liked
post.unliked
comment.created
comment.deleted
comment.liked
comment.unliked
post.bookmarked
post.unbookmarked
```

Payload:

```text
{version:1,eventId:UUID,type:<enum>,actorId:UUID,postId:UUID,commentId?:UUID}
```

No post/comment text, media, JWT, push token or credentials are in these events. Key is `postId`. The immutable event is stored as existing outbox `{kind:"socialInteraction",event}` **inside the mutation transaction**. Duplicate like/save/unlike/unbookmark transitions do not enqueue another social event. Publication occurs only after successful commit; outage retains the row with the existing claim fencing, lease, attempt count and backoff. Outbox publication errors do not fail a committed social operation.

Consumers validate the versioned event and recompute the actor/post interest from current canonical like, save, live-comment and live-comment-like rows. They do not apply incremental deltas or trust event ordering. Post locking serializes competing signal recomputations. Duplicate/reordered events converge to the same weight; unchanged weights do not move the interest timestamp, and zero-weight entries are removed. No event updates user-facing engagement counts: those always read canonical indexed relations.

The existing consumer propagates processing failure without deliberately advancing the failed message offset. Persistent outbox failures remain visible as retained rows/attempts; malformed Kafka records require operator diagnosis/retry or controlled quarantine. There is **no new automatic dead-letter topic or retry-exhaustion purge**. Broker loss after acceptance can replay an event; the projection is safe under that replay. Live broker failover/offset recovery was not tested here. Existing `fromBeginning:false` behavior remains for brand-new consumer groups; canonical history fallback prevents missing historic signal events from making Explore unavailable.

Ordinary post likes/comments retain their existing activity notifications. These separate events still use the same outbox and notification lifecycle.

## 6. Performance and correctness checks

* Canonical `_count` aggregation and batched current-user lookups replace inconsistent per-endpoint flags. No client counts or eventually consistent Kafka counters are used for engagement.
* Saved/comment read SQL call counts remain independent of returned row count: measured **6 versus 6** calls for 1/12 saved results, and **5 versus 5** for 1/12 comment results in the PostgreSQL-WASM driver test.
* Home feed now uses a follow-relation predicate rather than materializing an unbounded list of all followed account IDs into an `IN` list.
* Explore scores at most 500 posts and hydrates media/author/engagement details only for the requested page. Authorization scans only bounded snapshot IDs on cursor requests; ranking is not repeated per page.
* Comment-like writes lock the live post against deletion with `FOR SHARE`, then lock the target comment; separate comments on one post need not serialize on an exclusive post lock. Comment delete retains its existing post-first lock ordering.
* Bookmark create uses `createMany(skipDuplicates)` and its PK rather than a check-then-insert race; only real transitions enqueue events. Post deletion is excluded with a shared post lock.
* Native PostgreSQL `EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)` was actually run on isolated test fixtures for comment-like lookup, bookmark traversal and an Explore candidate query. The planner used the comment-like unique index and bookmark cursor index (bitmap scans on the small fixtures; bookmark plan also sorted). Plans are in ignored `.cache/social-query-plans.json`; these are not production-scale latency benchmarks.

The popularity aggregate and per-author discovery query still depend on the size of the 30-day live-post window. Large-scale deployments should profile these queries with representative data before introducing materialized global candidate pools/rollups. The implementation intentionally starts with a practical bounded-ranking algorithm instead of unnecessary ML or fabricated performance claims.

## 9. Operational limits and next steps

* **Privacy policy is deliberately fail-closed:** the existing schema has no approved-follow workflow, so a private account's posts and stories are owner-only even if a follow row exists. New follow attempts to a private account are rejected until follow requests are supported; existing follows are retained but do not grant content access. The existing authenticated `PATCH /users/me` profile endpoint now accepts `isPrivate:boolean`; profile reads return the flag. Explore never includes private accounts. Existing accounts remain public by default. Do not describe this as private-with-approved-followers until a follow-approval workflow is implemented. Existing external media/CDN copies or previously shared message previews cannot be recalled by this API.
* There is no block graph, moderation visibility enum beyond existing deletion/account state, formal interest taxonomy or impression tracking. Add those filters centrally when those product models are introduced.
* Ranking is heuristic/bounded to 30 days; no guarantee of globally optimal recommendations or a full archive traversal. Sparse users/pools can get short/empty feeds. Topics use hashtags, not semantic understanding.
* Interest projections are eventually consistent. Canonical fallback handles outages/new installs, but does not backfill every old interaction. A deleted comment can leave another comment-liker's historical projection stale until that actor/post is recomputed; this affects approximate ranking only, never exposed counts or authorization. A future reconciliation job can address historical projection cleanup.
* Snapshot expiry and seven-day seen cleanup occur on that account's next fresh request. Inactive accounts' expired rows remain until operator maintenance; schedule bounded cleanup of `explore_sessions.expires_at` and old `explore_seen.seen_at` using the added indexes. Keep the intended seven-day repeat-suppression policy when pruning. Outbox failure retention remains an explicit operator responsibility.
* The popularity cache and rate limiter are per process. A shared cache/rate-limit store and materialized candidate pools can be added after production profiling; no authorization data should be cached without a revalidation policy.
* Likes count all canonical like rows, not only currently active liker accounts. Comment counts exclude soft-deleted comments; physical deletes use FK cascades. Reads may observe subsequent concurrent operations under standard database read semantics; clients should apply authoritative later responses rather than assume counts never change.
* Monitor outbox attempts/oldest age, Kafka consumer lag, invalid event failures, candidate-generation latency and session/seen table growth. Permanently malformed Kafka records currently need operator remediation; automated quarantine/DLQ is a future operational enhancement.
